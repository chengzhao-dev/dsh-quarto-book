# 围栏与正文的配对

本文件只回答一个问题：代码围栏里给读者看的是声明还是定义，正文就只讲哪种话。

## 两种素材，两种话

| 素材 | 围栏里是什么 | 正文可以讲什么 |
| --- | --- | --- |
| 声明围栏 | `.h` 里的签名、成员、类定义 | 契约：参数、返回值、异常、边界、副作用、与其它接口的分工 |
| 定义围栏 | `.cpp`（或头文件里的函数体）里的实现 | 机制：用了哪个函数、什么表达式、是否复制、扫描顺序、为什么这样写 |

判据只有一句：**删掉定义文件，这句话还成立吗？** 成立是契约，不成立是实现。

## 三种合法配对

| 配对 | 围栏 | 正文 | 用在 |
| --- | --- | --- | --- |
| 契约型 | 声明 | 契约文字 | 定义平凡：单行 `return`、一跳转发、两行赋值 |
| 机制型 | 声明 + 定义 | 实现文字 | 定义非平凡，需要讲分支、算法或取舍 |
| 纯定义型 | 定义 | 实现文字 | 定义就在头文件（`constexpr`、模板），或声明已在本章前文出现过 |

补充一条**组合转发例外**：同一小节里几个一跳转发的定义可以合并成一个短围栏，正文讲它们如何组合；合并后仍遵守「正文只讲围栏里看得到的代码」。

## 不允许的写法

1. 声明围栏 + 实现文字（本节讲机制，读者手上却只有接口）。
2. 声明围栏 + 「完整实现见源文件」这类指路句：读者在书里看不到，等于没给。
3. 正文出现围栏里不存在的函数名或表达式（正文讲 `GetWinner`，围栏只有 `IsFull` 的声明）。
4. 声明与定义之间隔了整段机制解释，读者翻到围栏时讲解已经结束。
5. 定义不平凡却只写契约，再在「常见错误」或 Callout 里补一段机制。

## 平凡定义的判定

- 平凡：单次比较、单个 `return`、两行赋值、纯委托（`return Other();`）、只做一次边界检查后返回。
- 不平凡：含循环或分支组合、更新状态、与别的类型协作、需要解释「为什么不用另一种写法」。

平凡判例：`IsInRange` 的 `return row >= 0 && row < kRows && col >= 0 && col < kCols;`、`IsFull` 的 `none_of` 一行。

## 正反例（棋盘章的真实片段）

改前——声明围栏，正文讲定义：

```markdown
```{.cpp filename="board.h"}
  /// @return 任一方形成三连时该棋子类型；没有赢家时返回空。
  [[nodiscard]] std::optional<CellType> GetWinner() const;
```

`GetWinner` 扫描全部整行、整列与两条对角线，命中就返回赢家。
```

改后——组合围栏，正文对着代码讲组合：

```markdown
```{.cpp filename="game.cpp"}
GameResult Game::JudgeAfterPlace(const Board& board, Player player) {
  const auto winner = board.GetWinner();
  if (winner.has_value() && *winner == PlayerToCellType(player)) {
    return PlayerToWinResult(player);
  }
  if (board.IsFull()) {
    return GameResult::kDraw;
  }
  return GameResult::kInProgress;
}
```

`JudgeAfterPlace` 先看赢家再看满盘；`Board` 只回答有没有三连、是否满盘，结束与否由对局层组合。
```

## 与其它规则的关系

- **代码块门槛**（`steps/03-blocks.md`）：平凡实现不出围栏；本文件给的是「已经决定要讲」时该怎么配围栏。
- **正文与注释分工**：契约与边界写进 `///`，正文不转述；实现文字只补围栏里没有的上下文（为什么这样组合、和谁配合）。
- **检查器**：`scripts/verifying-content.py` 按 `###` 小节扫描，只有 `.h` 围栏而正文出现实现词时报 `decl-without-def`；「常见错误」「自测问题」「本章回顾」与表格行豁免。
