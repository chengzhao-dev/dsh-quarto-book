# 中文案例：术语与措辞对照

术语、译名与措辞替换的正反对照。

## 术语节奏

首次出现时就近放术语 callout（规则见 `steps/02-structure.md`），后续固定一种称呼。普通概念不加行内代码；命令、路径、文件名、关键字、API 和配置键使用行内代码。同一对象在同一页保持一种标记方式，链接标签内不嵌套行内代码。

一个概念全书只用一个词，统一术语与替换规则见 `steps/06-wording.md`。对照案例：示例章引言的「实现切片」改「阶段」后统称又停用，最终直接写具体目录路径。

## 游戏与对局

条文见 `steps/06-wording.md`「定用词：术语要稳」。「游戏」指作品或玩法整体，「对局」指具体一场；定义句用「游戏」，规则、落子与结果语境用「对局」，同一页不互换。

```text
不佳（定义句把作品整体说成一场对局）：
井字棋是两名玩家轮流落子的对局：先手用 X，后手用 O。

改写（作品用「游戏」，具体一场才用「对局」）：
井字棋是两名玩家轮流落子的游戏：先手用 X，后手用 O。本章演示一局对局。
```

判定信号：定义「X 是…」时用「对局」；同一段里「游戏」与「对局」互换指同一对象。

## 术语标签对照句

「ToFlatIndex 的声明」这种贴标签写法要改成什么：改成直接写位置事实。正文不给代码实体贴「是定义／是声明」标签，也不成对展开两者的区分——那是教 C++ 术语，不推进读者对状态面板工程的理解。位置与实现直接写具体事实（「换算写在 state.cpp」「常量在头文件里给出值」），「定义在 x.h」式位置动词不受限；声明引入名字、定义提供实体的辨析降为编辑与评审的内部口径，见 `steps/06-wording.md`「定用词：术语要稳」。以 示例章用数组存放九个数据项节改稿前为对照：

```text
不佳（块后给 `private:` 下的两行分别贴定义、声明标签，再总结「声明集中在头文件」）：
`cells_` 连同存储一起写出，是定义；`ToFlatIndex` 只给出函数名和参数表，是声明，它的定义写在 state.cpp。声明集中在头文件，`Board` 有什么就能看全，换算的实现细节跟着 state.cpp 走，不进头文件。

改写（删除标签段；换算函数体的位置由「换算一维下标」节导语交代，存储与 `private:` 下成员由本节导语与下一段展开）：
九个数据项的状态存放在 state.h 的一个数组里，数组声明在 `private:` 下，数组上方是下标换算函数 `ToFlatIndex`：……

`cells_` 的类型把长度写成 `kCellCount`：状态面板有多少格子，编译期就确定下来，代码里改不出别的长度。……
```

以 示例章改稿前同章自相矛盾为对照：

```text
不佳（同为完整枚举，一处称定义、两处称声明）：
Game::ApplyMove 每次操作都返回一个处理结果，定义在 state.h 里：……
先手是 X。流程用户用枚举表示，声明在 state.h 里：……
流程结果有四种取值，声明在 state.h 里：……

改写（位置动词只说「定义在 state.h 里」；函数体位置直接写「写在 state.cpp」，不贴声明标签）：
Game::ApplyMove 每次操作都返回一个处理结果，用枚举 PlaceResult 表示，定义在 state.h 里：……
先手是 X。流程用户用枚举 Player 表示，定义在 state.h 里：……
流程结果有四种取值，用枚举 Result 表示，定义在 state.h 里：……
state.h 里 `private:` 下的 ToFlatIndex 只写函数名与参数表，函数体写在 state.cpp。
```

判定信号：句子给围栏里的行贴「是定义」「是声明」「……的声明」标签，或成对解释两个词的含义（「声明引入名字，定义提供实体」进正文）；同章时而称声明、时而称定义说明标签用法本身不稳；「这份声明改不出别的长度」一类句子把带存储的成员叫成了声明。

## 访问说明符译名对照

访问控制相关概念点名时用 `steps/06-wording.md` 的决定词：`` `public:` `` / `` `private:` `` 下（或之后）的成员分别称「公开成员 / 私有成员」。自造比喻「公开段 / 私有段」读者对不上源码，一律禁用：

```text
不佳（「段」是自造比喻，读者要在源码里找「段」）：
`Board` 把存储和换算收在私有段，公开段只留下四个入口。

改写（写 `public:` / `private:` 下，成员称公开/私有成员）：
`Board` 把存储和换算收在 `private:` 下，`public:` 下只留下四个入口。
```

```text
不佳（「公共成员」与访问控制术语不一致）：
入口都是公共成员，调用方可以直接调用。

改写（用「公开成员」）：
四个入口都是公开成员，调用方可以直接调用。
```

判定信号：正文出现「段」「公共成员」「成员变量（作主称呼）」「方法（作主称呼）」等非决定词；C++ 概念点名时没有按术语全表写。

## 措辞替换

| 不佳表达 | 改写 |
| --- | --- |
| 对文件进行修改 | 修改文件 |
| 如果……的话 | 如果……，或……时 |
| 其实/简单来说/完全/非常/特别 | 删除，不保留无信息修饰 |
| 吃透/讲清/彻底理解 | 改成可观察的验证结果 |
| 错误被返回 | API 返回错误 |
| 刻意保持最小 / 刻意…… | 直接陈述程序做了什么、不包含什么 |
| 只可能来自 A，不可能来自 B | 写成可核对的排查范围：工程不含 B → 失败时先查 A |
| 由 N 段命令定义：A、B 和 C | 直接点名对象：这段规则定义可执行目标 app，规定产物目录、源文件和 C++20。 |
| 规则库 | 项目动态库（读者正文与代码注释、CMake 注释统一此定名） |
| 即胜着 / 更好的着 / 随机着法 | 马上能赢的一步 / 对当前用户更有利的一步 / 随机操作 |
| 占格操作 / 占格 | 向已有元素的格子操作 / 已占用 |
| 行优先（读者正文） | 按行依次排列；涉及下标用区间表述（第 0 行占下标 0–2） |
| minimax（读者正文） | 极小极大 |

## 可能性断言与作者姿态

诊断与范围用可观察事实，不用「只可能 / 不可能」式假确定性，也不用「刻意」等作者姿态修饰：

```text
不佳：程序刻意保持最小，只向标准输出写一行固定文本并返回 0。第一次配置、编译、测试如果失败，原因就只可能来自工具链，不可能来自游戏逻辑。
改写：它只向标准输出写一行固定文本并返回 0，不含任何游戏逻辑。第一次配置、编译、测试失败时，排查范围限定在工具链与构建规则。
```

```text
不佳：可执行目标由三段命令定义：输出目录、源文件清单和语言标准：
改写：这段规则定义可执行目标 app，规定产物目录、源文件和 C++20。
```

## 无铺垫的规则指称

导语能不能写遵循同一套规则：不能在规则本体给出之前写。以 首章明确流程行为节改稿前为对照。规则本体尚未给出就指称「同一套规则」，读者不知道「同一套」对着什么、规则里有什么；抽象指称必须落在读者已经看得见的对象上：

```text
不佳（规则未给出先指称，句子顺序也把交流形态放在流程构成之前）：
一次流程通过文本交流完成：用户输入行列，程序打印状态面板和结果。两名用户轮流在 3×3 状态面板上操作，程序的每一步回应都遵循同一套规则：

改写（先流程构成、再交流形态，导语直接点名下面的四项行为）：
两名用户轮流在 3×3 状态面板上操作，一次流程通过文本交流完成：用户输入行列，程序打印状态面板和结果。每一次输入，程序都按下面四项行为回应：
```

判定信号：句中出现「同一套」「这套」「以下规则」等指称，而所指对象在前文尚未出现 → 先给出对象再指称，或直接点名列表内容。

## 渐进披露元叙述

把 Agent 侧的写作策略念给读者听，是典型的 AI 味元叙述。正文直接陈述对象和结果，延后的内容保持沉默：

```text
不佳：语法细节留到后续章节真正用到时再展开。本章只需认清这段程序里被下游读取的两处结果：标准输出中的 Hello, World!，以及 main 返回的 0。
改写：这段程序对外可见的结果只有两处：标准输出中的 Hello, World!，以及 main 返回的 0。
```

判定信号：句子的主语是「本章 / 这本书 / 写作策略」而不是工程对象；内容在告诉读者「接下来不讲什么、什么时候才讲」。禁用词见 `steps/06-wording.md`。

不整词禁用「可能」：规划边界可写「按需评估」；技术命题「不可能改变结果」改为肯定表述（如「跳过不改变搜索结果的分支」）。

## 口语开场与规划套话

语气的完整标准见 `steps/06-wording.md`；以下两例是重构示例项目全书时的定稿对照。

开场把讲义口换成书面陈述（首章）：

```text
不佳：示例项目动手前先弄清三件事：用哪些工具、项目要处理哪些内容、代码按什么层次实现。
改写：进入示例项目实现前，先确认三件事：使用哪些工具、项目要处理哪些内容、代码按什么层次实现。
```

引言把元叙述换成三句：承接上一章、这一章要交出的结果、对应源文件。源文件用中文锚文本的 GitHub 链接给出，不写行内代码路径：

```text
不佳：本章让单次动作可靠起来，先明确交付的行为与测试边界；内容的落点是 src/目录在真实开始实现时创建。本页是规则设计页，尚未对应可运行的实现目录。
改写：状态面板与状态建立了状态模型。本章定义单次操作的合法与非法处理及其测试边界；对应实现在 [操作合法性实现目录](https://github.com/your-org/your-book/tree/main/src)，实现并通过验收前按设计页阅读。
```

## 空泛套话与编辑残留

以操作节导语改稿前为对照（规则见 `steps/06-wording.md`「情况：空泛套话与编辑残留」）：

```text
不佳（套话、编辑腔与客服腔各一处）：
下面我们来看构建配置。CMake 在这里扮演着至关重要的角色，它无缝衔接了编译与测试，为后续扩展赋能。

改写（只留对象与动作）：
CMakeLists.txt 把编译和测试串起来：先 cmake --build build，再跑 ctest。
```

判定信号：删掉「下面我们来看」「至关重要」「无缝」「赋能」后，读者取走的信息不变；同一动作在一段里换了三个说法；正文出现对读者的招呼或「如有疑问请联系」。
