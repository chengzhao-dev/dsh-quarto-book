# 中文案例：结构与形态对照

章与节的结构、标题、目录树与开场的正反对照；条文权威见各节点所指的规则文件。低频的章级定稿对照在 `appendix/chinese-style.md`（不进检索索引，仅人审时读）。

## 正确形态正例

正确的段落形态长这样，写正文时可直接对照：

```text
正确（段落导语：工程语境 + 一句判断依据）：
这段构建规则定义可执行目标 app：先规定产物目录，再列出源文件，最后要求 app 使用 C++20。
三条命令各管一步，读者按顺序核对即可。

正确（收束句：指向可观察结果）：
看到 Hello, World! 后，就完成了本章的实践目标。

正确（排查句：可核对的排查范围）：
第一次配置、编译、测试失败时，排查范围限定在工具链与构建规则；工程不含游戏逻辑。
```

正例的判定条件：主语是工程对象；一句话一件事；验收句指向能看到的结果而不是宣告章节状态。

## 定结构：标题只留对象名

条文见 `steps/02-structure.md`「标题字数」「形式规则」。两个旧标题都在旧字数上限内，仍是一句步骤说明：指示、过程动词和关系词把真正的对象挤到末尾；目录、侧栏和页内 TOC 需要的是对象名，不是把导语缩进标题。改写在定结构：先圈出目录里要扫到的对象，删掉指示、过程和数量，再检查同级句式是否一致。

**定结构（示例章「记下流程数据」下两个三级标题）：**

```text
不佳（「记下」是过程动词，「这一步」「用到的」是指示与关系，对象「类型」被挤到末尾；「收进这一次」同样只留下「局」这个对象）：
### 记下这一步用到的类型
### 收进这一次

改写（标题只留对象名；「操作类型」会漏掉整局结果，四个类型合称「流程类型」，`Game` 的四个数据成员合称「流程成员」）：
### 流程类型
### 流程成员
```

判定信号：标题字数合规，但删掉指示（这一步、这次）、过程动词（记下、收进、用到）后对象才露出来；同一二级下的三级标题一半是动宾、一半是名词。

## 小节标题抽象与首句无中心

小节标题用了读者没学过的术语怎么办，与一段压缩多个论断怎么改，是同一类病。示例章依赖节的两次改稿对照：第一轮标题读不出动作对象，首句堆齐名称后才在句尾给出结论；第二轮标题动作化了，但「使用方」仍是读者未建立的术语，正文一句压缩三个论断，读者无法逐条核对（规则见 `steps/03-blocks.md`「小节标题与正文对齐」）：

```text
不佳（标题抽象 + 首句无中心）：
## 确认依赖方向
`state.h` 和 `state.h` 是规则库的对外头文件，终端程序通过它们使用状态面板和操作规则，`tests/` 也读取它们验证操作结果。依赖都指向规则库，测试因此不需要启动终端程序。

仍不佳（标题动作化，但术语未建立 + 一句压缩三论断）：
## 查看规则库的使用方
终端程序和测试目录都依赖规则库，用的都是它对外的两个头文件 `state.h` 和 `state.h`。依赖都指向规则库，测试规则时不需要启动终端程序。

改写（内容不该在这一章出现：删除该节，事实下沉到 示例章 CTest 首次出现处）：
示例章保留目录树小节收尾；示例章「执行验证脚本」节写：`tests/` 里的两个测试文件直接读规则库头文件 `state.h` 和 `state.h` 来核对操作规则，测试不启动终端程序。
```

判定信号：读者无法把标题的名词短语还原成具体对象或动作；首句要读到句尾才知道段落中心，或一句话里并列三个以上名称而没有中心句统领；标题或正文用了读者此刻尚未建立的概念术语（如「依赖」「使用方」「动态库」「稳定边界」），正文却没有读者可核对的实物支撑——此时先问内容该不该出现在这一章（删除或下沉），而不是只换措辞。

## 目录式堆砌

一句里串多个交付物或动作时，读者拿不到「本章唯一结果」，正文退化成说明书目录（删改口诀见 `writing-quarto` 技能 `steps/01-task.md`）。两个 canonical 反例来自 示例章改稿前的原文：

```text
不佳（章引言交付物清单，一句串四个交付物）：
本章把规则核心拆成独立组件并编译成动态库，定义状态面板与状态的值类型，
固定查询、操作与结果三个入口，并引入 GoogleTest 编写规则测试。

改写（引言只承诺一个可验证结果，细节进小节）：
本章把规则核心编译成动态库，并用 GoogleTest 固定状态接口的行为。
```

```text
不佳（树后说明书复述，逐项重讲树注释已交代的职责）：
规则库组件 example/、终端程序组件 apps/ 与测试目录 tests/
各自带 CMakeLists.txt，顶层规则只做工程声明、产物目录与组件组合。

改写（删复述，至多一句关系收束）：
三个组件各自带构建规则，由顶层规则组合成一个完整工程。
```

判定信号：引言一句话里用顿号或「并」串起三个以上交付物；树后段落逐项复述树内行尾注释。清单删掉后读者仍能说出成功判据，清单就该下沉到小节。

## 目录行替子文件说话

示例章改稿前，目录行把子文件的职责也写进来，读者会以为「打印与读入」是目录本身的任务；目录只说明这里装什么，文件才写职责（规则见 `steps/03-blocks.md`「情况：目录树」）：

```text
不佳（目录替子文件说话，同棵树的层级也不一致）：
├── apps/          #/ 终端程序：打印与读入
│   ├── include/   #/ 终端程序的对外接口
│   │   └── cli.h  # 终端交互
├── cmake/         #/ 构建用的 CMake 脚本
└── tictactoe/     #/ 动态库：棋盘与对局
    ├── include/   #/ 动态库对外接口
    └── src/       #/ 动态库实现：随库一起编译
```

```text
改写（目录只写装什么，文件写职责）：
├── apps/            #/ 终端程序
│   ├── include/     #/ 终端程序接口
│   │   └── cli.h     # 终端交互
├── cmake/           #/ 构建脚本
└── tictactoe/       #/ 动态库
    ├── include/     #/ 动态库接口
    └── src/         #/ 动态库的实现
```

判定信号：目录注释出现冒号、顿号清单或替子文件写任务（「打印与读入」「棋盘与对局」），就是越界；目录只用名词短语（不超过 16 个显示列），文件注释才承担对象与动作（不超过 28 列、只列 1–2 项）。

## 树后读法句问答式并列

```text
不佳（树后读法句问答式并列）：
目录树在同一行里写出文件位置和职责，文件名回答“文件在哪里”，行尾注释回答“它负责什么”。

改写（直述机制，一句收束）：
目录树在同一行里写出文件位置和职责：文件名给出位置，行尾注释说明职责。
```

判定信号：树后句子前半句先概括，后半句再用「X 回答 A，Y 回答 B」拆开重讲。

## 树后换对象收束句

目录树后能补一段工具配置的分工吗：不能换对象。示例章改稿对照：树后两句把主语换成 `.clang-format`、`.clang-tidy`、`.clangd` 三份工具配置，而本节标题和清单的对象是四个目录；第二句「三份配置只描述工具怎么检查代码，CMake 构建规则不依赖它们」还与仓库事实不符——`.clangd` 的 `CompileFlags.Add` 是未构建时的解析兜底，不是检查规则，CMake 会为 clangd 导出 `build/compile_commands.json`（规则见 `steps/04-paragraphs.md`「段间：过渡句只在话题切换处」与 `steps/03-blocks.md`「小节标题与正文对齐」）：

```text
不佳（树后收束句换成本节清单没有的对象）：
└── build/    #/ 构建产物目录
    ├── bin/  #/ 可执行文件
    └── lib/  #/ 项目动态库文件

构建脚本用格式和静态检查两份配置验收源码，编辑器配置不参与编译。三份配置只描述工具怎么检查代码，CMake 构建规则不依赖它们。

改写（删除；这些句子的对象是工具配置，不是本节四个目录，删除后主线仍闭合）：
（树后不接段落，直接进入下一节；工具链分工留给讲构建与检查的章节）
```

不原句搬家的原因：第二句不能下沉到操作章——`.clangd` 不是检查规则，CMake 会为 clangd 导出编译数据库，「三份配置互为『只检查、构建不依赖』的同一类东西」这一判断本身不成立；原句搬家只会把不准确论断带进新位置。

判定信号：树后段落的主语不再是本节标题清单里的对象；或用「只…不…」把多份配置压成同一类。

## 独立说明书段与元标签开场

以 首章工具节与 示例章对照表为对照。相邻两段各讲各的、表格用元标签开场，都是衔接缺失（规则见 `steps/01-task.md`）：

```text
不佳（两段各成独立说明书）：
实现用 C++20，构建规则由 CMake 编写、Ninja 执行，编译器是 Clang，测试由 CTest 运行。命令默认在 WSL Ubuntu 中执行；Windows 用于兼容性验证和浏览器展示。

代码按编号组织在示例项目代码目录下的编号目录里，每个目录都能独立配置、编译、测试和运行。

改写（第二段段首接住第一段的对象）：
实现用 C++20，构建规则由 CMake 编写、Ninja 执行，编译器是 Clang，测试由 CTest 运行。命令默认在 WSL Ubuntu 中执行；Windows 用于兼容性验证和浏览器展示。

这些工具用在示例项目代码目录下的编号目录里：每个目录都是完整项目，能独立完成配置、编译、测试和运行。
```

```text
不佳（对照表元标签开场）：
配置与构建是两个容易混淆的词：
改写（先写关系再引出表格）：
配置改计划，构建按计划编译，两者由不同工具承担：
```

判定信号：第二段删掉后第一段仍完整成立、彼此无引用；或表格前的句子只宣告「接下来是对照」，不含工程关系。

## 自测问可观察结果

以 示例章自测第 1 题改稿前为对照。「为什么后手不能在开局直接落在中心」把「中心」当成读者已认识的概念，本章正文从未定义中心格；拒绝的原因也与格子无关——空状态面板上轮到甲方，O 落在哪一格都会被拒绝。题面用本章没说全的情景提问，读者会以为中心格另有规则（步骤：定结构；规则见 `steps/02-structure.md`「六段块序列」）：

```text
不佳（题面用了本章未定义的概念，情景没说全）：
1. 为什么后手不能在开局直接落在中心？

改写（情景用本章已用过的词说全，问一件可观察结果）：
1. 状态面板仍是空的，当前轮到甲方，这一步的用户是 O。这一步会被写下吗？

   ::: {.answer}
   不会。当前用户是 X，状态面板仍是空的。
   :::
```

判定信号：题面出现本章正文从未用过的概念（如「中心」「开局直接落」）；或情景里「哪一格都一样」却单点某一格；或问「为什么不做成另一种」。题面里的每个细节都要改变答案；只有本章写了原因、而且情景已经说全时，才用「为什么」。

## 输出引言的结构元词

以 首章查看终局输出节二轮改稿前为对照。引言向读者描述输出文本自身的结构分类，读者要先换算一遍才知道看什么；引言直接说出阅读动作与关注点，结构与顺序交给随后的引导词列表呈现：

```text
不佳（引言给输出贴结构元标签，「并列」描述的是文本而非状态面板）：
这段输出从上到下包含三个并列部分：

改写（说出阅读动作与关注点，三项由引导词列表承接）：
阅读这段画面时，可以依次关注三处：
```

判定信号：引言含「并列部分」「并列区域」等描述文本自身结构的元词，删去后读者仍知道看什么。拦截面见 `writing-quarto` 技能 `scripts/verifying-content.py` 的 FORBIDDEN_PATTERNS。

## 标题口语化与章题脱节

条文见 `steps/02-structure.md`「形式规则」「纵向承诺链」第 9 条。标题先看目录里要扫到的对象：人称、劝诱和时间从句都是导语的事；章题再看正文的主对象，title 承诺 A 而多数任务节在讲 B 时，改 title 或重排结构，不靠导语补丁。示例书首章改稿前后的对照：

```text
不佳（人称 + 劝诱；时间从句起头）：
## 自己走一局
## 输入之后的回应

改写（对象或「动词 + 具体宾语」；时间关系下放导语）：
## 对局演示
## 落子规则
```

```text
不佳（title 对局规则，正文主对象是程序回应）：
标题：对局规则
引言：程序对每一次输入作出回应……
任务节：输入之后的回应、自己走一局

改写（title 的对象在引言、任务节和回顾三处兑现）：
标题：对局规则
引言：井字棋是两名玩家轮流落子的对局……
任务节：落子规则、胜负判定、对局演示
```

判定信号：标题带「自己」「跟我」「试试」或「…之后」「…之前」；把 title 与各 `##` 的中心名词并排，多数 `##` 的中心名词不是 title 的对象。

## 八条线拆成两个实体标题

标题在数条目时，读者不知道这一节要认识哪个实体；正文也容易把坐标表、成线判断和归属句挤在同一节（规则见 `steps/02-structure.md`「形式规则」）：

```text
不佳（标题数条目，一节混讲坐标表、算法和归谁用）：
### 八条线
八条线的坐标写在 board.cpp 里，存成一张 constexpr 常量表。HasLine 与 IsLineComplete 共用它。
Game 和 Ai 调用查询，不读它，所以不放进 Board 类里：
（kLines 围栏）
（算法旁白与 HasLine 围栏）
```

```text
改写（拆成两个实体标题，每节只讲一个实体）：
### 线坐标表
（只引出 kLines 围栏）
### 成线判断
（只引出 HasLine 围栏；共用 kLines 留在三连判定节）
```

判定信号：三级标题是「八条线」「三种类型」「四个入口」这类集合数量；正文先数条目，再讲其中一个实现，最后补归属。处理：条目能各自成实体就拆标题；不能就把标题改成承载它们的对象。
