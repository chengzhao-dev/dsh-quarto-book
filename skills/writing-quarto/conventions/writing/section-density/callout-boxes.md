# Callout 与盒子密度

Callout 的重量平衡、盒子比例与元素边界；主线闭合见 `conventions/writing/section-density/main-line.md`。

## 正文与 Callout 的重量平衡

读者会把长而密的正文当成当前主线，把紧随其后的短提示当成脚注。正文同时承担先后状态、正常现象、成功判据和执行范围，而 Callout 只剩一句术语解释时，两者的信息重量差距过大，新手容易跳过提示，之后又把提示符误解成命令行语法。

修法必须同时发生。正文按状态节点拆短，让每个状态节点各有安放处。Callout 恢复并列字段的列表结构，让内容本身具备可扫读的重量。只放大 Callout 会让所有可选提示都像重点，只拆正文又会让尾部提示继续像脚注。必经动作始终留在正文。成功判据只有在不要求读者继续操作、且需要根据所见界面继续解释时，才可以和解释组成结果型 Callout。

## 结果型 Callout 的边界

把提示符判据留在正文，再把符号含义放进 Callout，会把同一个观察对象拆成两处：读者先看到一个结论，跳过提示框后又不知道如何理解它。把两部分都塞回正文，则会让结尾重新变成长段。结果型 Callout 解决的是这种"判据本身也是解释对象"的局部问题，不是把成功路径移出正文的通用许可。

使用时必须同时满足四点：成功判据是稳定、可直接观察的界面或状态。判据需要继续拆解字段、范围或含义。提示出现后本任务没有其他必经动作。正文已经用检查动作和明确的前瞻完成交接，且 Callout 首句直接兑现该检查动作。若后续还要输入命令、做选择或根据结果修复，判据必须留在正文操作位置。

"含义和范围如下"只说明后文目录，没有告诉读者要对照什么。Callout 再从"出现……"重新建立条件，会让同一次判断被拆成两次起句。改写时，正文提出"请对照下面的格式确认结果，并了解后续范围"，Callout 首句直接给出"看到……说明……"。正文负责建立检查动作，Callout 负责呈现判据，二者接力而不重复全文。

## 命令、输出与细节各司其职

命令是输入，输出是观察，正文是判断依据。三者混在同一个代码块或连续多个解释段落中，会让读者自己筛选"哪些行要复制、哪些行只是说明"。因此闭环目标、命令和成功判据各保留一个权威位置，操作小节拥有命令与验收，回顾和相邻段落只补充新增信息。路径、版本号等随环境变化的输出应展示可识别的典型形态，并给出"每项都有非空结果"这类稳定判据，而不是要求逐字匹配示例。成功判据与证据层级相称的要求见`conventions/writing/chapter-structure/task-sections.md` 的知识文件「术语与验证策略」。

## 盒子与正文的比例

盒子按最小模块计：一个模块一块代码、表或图；同一三级标题两个模块时可以有两块，中间必须有衔接句。Callout 不算这块主内容。盒子指代码块、表格、提示框、引用块、图表容器，含 `{mermaid}` 图与 `{python}` 坐标图单元。它们底色与边框一致、左右内缩相同，连续出现时读者分不清内容边界，只能靠滚动位置感知，页面从「读一段做一步」退化成「抄一屏」。因此一条主线动作配一段自己的承接正文，相邻盒子最多一处，其余被正文隔开。每两个盒子之间至少有一段交代判断依据的话；代码块与图之间的固定桥接序列见`conventions/writing/qmd-element-cases/layout-cases.md` 的知识文件。

修法是补承接正文，而不是删盒子。盒子承担可复制性，正文承担判断依据，两者不可互换，代码块删到只剩命令不会自动产生判断依据。

代码块前后的文字重量也应服务同一个任务闭环。代码块前至少说明读者要完成什么、在哪里执行以及执行后会发生什么；代码块后只说明下一步、可观察结果或一个必要的新人解释。若提示符、参数含义等补充信息不影响主线执行，可在主线结果确认后放进一个短 Callout；Callout 只解释新信息，承载边界见`conventions/writing/qmd-element-cases/layout-cases.md` 的知识文件「Callout 克制且尾置」。

密度比例不设硬阈值。盒子多少、正文长短同时取决于视口宽度、字体度量和 Quarto 版本的 DOM 结构，任何一项变化都会让历史数值失效，基于 DOM 或截图的硬编码门禁只会在与密度无关的改动上误报，仍然禁止。`verifying-content.py` 保留一条软门禁：同一小节内两围栏（含 `{mermaid}` 与 `{python}` 单元）之间只有空行、没有桥接正文时报 WARN，提示人工补承接句；WARN 不判失败，人审与对照案例仍是叙事的主检查。

## 元素边界

细节升级为标题的门槛见`conventions/writing/heading-fit/hierarchy.md` 的知识文件。常见错误使用三级结构，是因为目录负责导航、具体症状负责识别、有序步骤负责操作。具体写法见`conventions/writing/chapter-structure/skeleton.md` 与 `conventions/writing/qmd-element-cases/block-loop.md` 的知识文件。

这种分层与页面整体的六段块序列并不冲突：它只收束任务段内部的阅读路径，不重新定义引言、任务序列、排查、自测和回顾的页面职责。

## Callout 尾置的原因

Callout 是视觉上独立的盒子。把它插在段落、命令或输出之间，会让读者误以为提示框也是必经步骤，主线因此被切断；可跳过与隐藏的承载边界见`conventions/writing/qmd-element-cases/layout-cases.md` 的知识文件「Callout 克制且尾置」。术语解释型 Callout 是唯一就近放置的例外，写法见`conventions/writing/qmd-element-cases/layout-cases.md` 的知识文件。

"目标 → 动作 → 结果 → 补充"能同时照顾首次执行和回看细节的读者。它把必须完成的内容放在主线，把可选解释放在尾部，也避免在开头只有一句目标、末尾却集中堆叠参数和手册链接。

## 目录树只展示当前任务需要的文件

目录树先尊重磁盘事实，再删除不影响当前任务的缓存和构建产物。`build/` 是否展开取决于当前任务是否需要认识产物的位置：布局章展开 `bin/` 与 `lib/` 建立完整目录认知，验收章展开它核对产物；只讲源码的章节保持折叠。

正文只强调读者当前需要识别的文件。树后正文的条文见`conventions/writing/section-flow/transition.md` 的知识文件。展示顺序按工程理解推进：接口与实现（源码）、构建规则、测试与运行产物；实现章正文按同一顺序展开叙事，设计与实现先于构建规则，再进入测试（顺序见`conventions/writing/chapter-structure/skeleton.md` 的知识文件）。

保留的节点按 `tree -a` 字母序展示，不按讲解顺序重排；本章不讲的文件整枝删掉，不展开 `build/_deps`、目标文件、每个 `CMakeLists.txt`。句子里的目录个数、列表条数、树里的顶层目录个数，三者相同。

树内行尾注释承担文件职责说明：目录注释以 `#/` 开头，文件注释以 `#` 开头并比目录的 `#/` 右移 4 列；注释是名词，不写动词、括号，也不写「见某一章」。每个展示文件都有行尾注释，一短语一职责，不在树内展开解释。树后正文见`conventions/writing/section-flow/transition.md` 的知识文件；GitHub 链接放在该文件首次被精讲的正文处。与主线无关的子目录折叠为单行目录，不展开子文件。

正式 C++ 入门页不用 Mermaid 表达线性构建流程，改用标题和文字连接。复杂数据流确实难以文字说明时，才使用独立图表并给出一句结论。

## 行内代码只标记需要逐字识别的对象

命令、参数、文件名、路径、配置键、API 和标识符使用行内代码。Ubuntu、Windows 和 VS Code 作为普通平台名称时不加反引号。标题与导航不使用行内代码，形式规则见`conventions/writing/heading-fit/hierarchy.md` 的知识文件。

同一对象在同一页保持一种标记方式。链接标签内不再嵌套行内代码。行内标记连续出现时，改用完整句子减少读者来回切换字体。

标记边界与术语节奏的执行规则见`knowledge/cases/chinese-style/wording-cases.md` 的知识文件，本文件只解释为什么需要克制。
